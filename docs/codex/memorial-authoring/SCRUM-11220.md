## Delivered behavior

- Editing a built-in template creates a personal ID/revision and retains the built-in origin. Personal edits increment that template's revision; save-as-new creates a separate ID. Old drafts retain their full template snapshot and final document after template changes or deletion.
- The template library persists favorites, order, default selection and restore operations. Catalog listing follows saved order, including after edits or reopening. Restore reinstates the selected built-in without deleting personal versions; deleting a personal default falls back to the first remaining ordered template.
- Draft and library stores use the planned `AiDesign/Authoring/Drafts/<id>/` and `AiDesign/Authoring/Templates/` roots. Each store holds a `FileShare.None` lock around reading current authority, CAS and publication. New drafts require `expectedRevision:null` and start at revision 0; successful saves increment storage revision independently of template revision.
- Each committed version is a unique `revision-<versionId>.json` envelope with its previous version ID. `current.json` names one exact version and revision; reads never choose a newest file. A bounded validated JSON reader rejects corrupt, unsupported, mismatched or null payloads. Polymorphic prompt parts roundtrip using explicit text/image discriminators.
- Filesystem operations reuse `AiDesignOwnedStagingFiles`: parent directories stay pinned for the store operation, a verified version handle denies writes/deletion through pointer publication, and the pointer replaces atomically. A caught failure rolls back only the exact version/temp files created by this operation. Committed history and unowned files are never cleanup targets. Reparse ancestry is refused.
- The module creates, reads and saves non-image edits, preserves the actual final text when fields change, requires preservation before recomposing manual text, and keeps the first composition separate from later final documents. Template/mode changes publish only after durable snapshots exist; a failed publication leaves the old head readable. Export takes the final document verbatim and explicitly marks unresolved image references. All incoming collections are detached before asynchronous waits, and persisted/returned snapshots expose read-only collections.

No SQLite migration, v1 Request/schema change, package addition, UI wiring, automatic generation, production activation or deployment is included.

Four Important findings, no Critical/Minor findings: revision handle closed before pointer commit; null payload exception; ignored catalog order; overwritten first composition. Each received a regression test that failed before the fix, followed by a single fix pass and 66/66 passing targeted tests. No second review or independent post-fix approval is claimed.

Scope decisions and consequences:

1. A2 reopens the last successfully saved draft head and retains linked history on disk. The approved interface exposes only `ReadAsync(id)`; a supported history-read/reopen seam and prior-version UI remain necessary for A5 before claiming user-facing history browsing.
2. Images, detailed confirmation invalidation and window-close behavior remain A3, A6 and A5/A7. A2 delivers persistence and non-image module commands, not the complete workbench.
3. Termination during first library initialization can leave orphan history without a pointer. Reads fail closed instead of silently resetting over history; this exceptional state needs explicit diagnosis/recovery. Automatic orphan adoption/cleanup is not implemented or claimed.
