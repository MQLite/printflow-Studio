## 1. Decision and evidence vocabulary

Recommend one **test-only entry with an explicit isolated composition**, reusing the real `MainWindow`, its DataTemplates, `ShellViewModel`, `NavigationService`, product views/view models, workflow engine, session services, SQLite repositories, image/trim/review services and NTFS delivery implementation. Replace only external processing, workstation facts/authority, OS integrations at their containment boundaries, and explicitly scripted failure stimuli. Do not instantiate `PrintFlow.App.App` or call installed startup. Do not build another UI or state machine.

The minimal change is a test-owned bootstrap/composition and narrowly scoped boundary decorators, with a small scenario manifest and the existing input/capture facilities. Normal product startup and production contracts need no change for this design. A later implementation must prove this is sufficient; an unexpected product seam requirement returns to the owner for a bounded amendment, not an ad hoc production bypass.

## 3. Isolation contract and construction order

**PROPOSED:** accept an explicit absolute local NTFS run root `R`, newly allocated for this run under an owner-selected nonproduction test parent. No implicit root, working-directory resolution, environment-variable expansion, installed settings, production DB copy or customer input. First validate the full resource plan without constructing a service provider, SQLite factory, workspace, guard, writer, decoder, native dialog or WPF window.

Topology (all names are proposed): `R/state/app.db`, `R/state/automation-lease.db`, `R/state/instance.lock`, `R/workspace/`, `R/fixtures/inputs/`, `R/fixtures/returns/`, `R/preset/`, `R/delivery/`, `R/recycle/`, `R/evidence/`, `R/diagnostics/staging/`, `R/diagnostics/export/`. Delivery is a sibling of workspace/state/evidence, because the real delivery service refuses protected managed roots. Do **not** pass all of R as a protected delivery root and thereby disable legitimate save. Instead protect state/workspace/preset/fixtures/recycle/evidence/diagnostics, and allow only the designated delivery subtree through the containment decorator.

Before the first write, canonicalize paths and validate path-component boundaries case-insensitively; reject root/parent equality, ancestor/descendant overlap with configured installation/production/default locations, UNC/device/extended path aliases, alternate data streams, rooted relative components, traversal, volume roots, and any reparse component or unresolved ancestor. Reject hard-linked input files (multiple link count) and hold/check file identity when admitting bytes; a text prefix check is insufficient. Reject unexpected existing run-root contents. Use a CreateNew ownership manifest and exclusive instance claim only after validating the selected parent; record run ID, root identity, resource paths and candidate identity. A resume requires that same validated ownership manifest, unchanged candidate/scenario and inactive prior owner; it is not permission to adopt an arbitrary existing directory.

Revalidate containment at each service boundary, including paths loaded from the isolated DB, not just after a picker. Validate directory/file identities immediately before operations; hold ancestor handles that prevent renaming/reparse substitution for the operation where feasible. If the chosen Windows APIs cannot safely enforce a particular operation, refuse that operation and mark the corresponding scenario unsupported until resolved. This is a same-user acceptance harness, not a security sandbox against an adversarial administrator or a promise that Windows performs no external I/O. OS/framework assemblies, fonts, locale, shell and process identity reads are normal; PrintFlow-owned data writes remain under R. Native shell dialogs may browse and OS-cache locations outside R; PrintFlow must not import/read selected file contents or write there.

After explicit future implementation authorization only: validate plan → create owned root/manifest and claim `SingleInstanceGuard` with explicit path → create one local SQLite factory and migrate the isolated DB → register/validate the allowed graph → obtain synthetic preset evidence → real recovery once → bounded real diagnostic retention → real persisted culture restore → publish actual startup summary → resolve shell/navigation. No fixture operation can race recovery. Refused guard/configuration/schema/recovery yields no usable shell. Retention failure remains a warning preserving uncertain evidence, matching current startup semantics. Do not fabricate successful recovery or a production-ready startup status.

## 6. TIFF screenshot trace — source-derived cause, no fix

**HISTORICAL OBSERVATION:** the prior SCRUM-11154 packet's `screenshots/guidance-tiff-en-1000x700.png` visibly shows a 6×5 pixel preview, save card “Print TIFF · 0.5 × 0.4 mm” and output row “200 × 150 mm (2362 × 1772 px at 300 dpi)” for `guidance_200mm_CMYK_W.tif`. It is an off-screen 96-DPI frame, not a new workstation capture. Its hash/provenance is in the new packet manifest.

**SOURCE FACT chain:**

1. `tests/PrintFlow.Tests/Integration/Ui/ReviewGuidanceLayoutTests.cs`, `The_review_picture_keeps_its_area_and_the_guidance_stays_in_the_details_column`, opens `ReviewGuidanceSetup.OpenAtAsync(h, "tiff")` and captures the matching filename.
2. `tests/PrintFlow.Tests/Fixtures/ReviewGuidanceSetup.cs:TiffAsync` calls `FinalSaveFixtures.TiffService` and `TiffAtFinalReviewAsync(... outputName: "guidance")`.
3. `FinalSaveFixtures.TiffAtFinalReviewAsync` defaults width to 200 and imports `h.WriteSourcePng()`. `SessionServiceHarness.WriteSourcePng` produces `SyntheticImages.Png(6, 5, alpha: true)`, whose default DPI is 300. `NextTiffSizeAsync` uses `SetPrintDimensions(PrintDimensions.FromMillimetres(200, 150, Custom))`, then W1 branch and StartStep.
4. These are maximum-box semantics: the source is smaller than the bounds; the preparation retains 6×5 projected pixels (resolution-only). `SyntheticProductionTiffProcessor.GenerateAsync` writes the preparation's `ProjectedPixelWidth/Height` using `ProductionTiffFixture`; it does **not** arbitrarily force all outputs to 6×5 and is not the default CopyApprovedInput fake.
5. `src/PrintFlow.Workflow/Services/ProductionTiffReviewService.cs:PreparationFor/PhysicalMillimetres` selects the producing attempt by this output revision, then computes physical mm from its preparation pixels at production DPI. Decoded TIFF pixel/DPI is only the fallback when preparation is absent. For this fixture, 6×25.4/300 = **0.508 mm** and 5×25.4/300 = **0.4233… mm**. `SessionViewModel.FinalSave.cs:TiffMillimetres` uses output-bound offer metadata, or this exact pending review payload; formatted at one decimal it displays 0.5×0.4.
6. `SessionService.cs:BuildPrintOutput` persists `stateBeforeFinish.Dimensions`; `SessionView.cs:PrintOutputView.From` passes `output.Dimensions`; `SessionViewModel.cs:PrintOutputRow` formats those width/height/pixel/DPI fields. That is the retained **200×150 maximum box**, including nominal 2362×1772 conversion, not the producing preparation's physical output. `ProductionTiffReviewService` explicitly documents why the box must not be reported as output physical size.

**Conclusion supported by source:** the frame combines two real but semantically different data projections for one output. The tiny fixture makes the difference conspicuous; synthetic TIFF generation follows the projected preparation. This is a source-supported output-row presentation mismatch (retained maximum-box dimensions presented beside actual physical-size guidance), not evidence of a Photoshop/physical conversion failure or corrupted synthetic file. The screenshot alone cannot prove historical DB bytes or the exact executed binary; no historical DB reconstruction or runtime reproduction was done. Scope beyond this frame, and the eventual product correction, remain open. Do not hide either value, falsify metadata, fix the product or amend historical evidence in this design task.
