# SCRUM-11151 — failure wording for the owner's bilingual copy review

Task `PF-OPUX-v1-SCRUM-11151-impl-v1`. This page holds the **final shipped wording** of the 16 listed keys and the localized helper strings, in English and 简体中文, so the product owner can review it. The review is still **open**: nothing here has been accepted or waived yet.

The per-key evidence (every consumer, producer family, side-effect boundary and why each claim holds) is in the [source-to-copy matrix](SCRUM-11151_PLAN.md#source-to-copy-matrix--shared-failure-sentences). It is not repeated here.

## How to read it

- **No sentence contains a code.** The exact code of the failure a notice describes sits in a collapsed **Error details / 错误详情** directly under that notice: "Code / 错误代码", the code, and the hint below. A failed step's stored failure keeps the existing Error details button, which opens that same attempt.
- **Shared sentences avoid unconditional Run/Retry advice.** Each `Failure_*` sentence is shown for every producer of its code: on the status line of a failed step, inside the processing-screen wrapper, inside the colleague-correction messages and on the Error details page. So it says what happened and only what is true on every path. The screen adds the next step.
- **Retry is never named in this copy.** On the processing screen the next step is the status line at the top, which names Retry / 重试 only when Retry is offered. A job waiting for a colleague keeps pointing at importing the corrected image. Neither Run step nor Retry is suggested there.
- **"Nothing was changed" appears only where it is proven**: opening a job (a read) and Settings (one rolled-back write). Abandon says only that nothing is deleted. Recovery warns that part of it may already be recorded.
- **Every shared sentence ends with the one universal guarantee**: PrintFlow never overwrites or deletes the user's original file (design invariant §18.1). Approved results are not claimed unchanged, because on the same codes a final TIFF can be promoted or recycled before a commit that can still fail.

### How the processing-screen notice is put together

`[Session_ActionFailed or, for PersistenceError, Session_ActionUnconfirmed]` with the failure sentence in `{0}`, then:
- `Session_ActionFailedNext` once the job has been read again;
- `Session_ActionFailedNextStale` if that read failed;
- nothing while the read is still running.

Sentences are joined with a space in English and without one after "。" in Chinese. A later notice or failure always replaces the earlier code. Changing the language re-words the same notice and reads or sends nothing.

## What the owner is asked to check

1. Each sentence reads naturally to a beginner in both languages, and the Chinese is consistent with the glossary (处理任务, 错误详情, 同事或主管).
2. Nothing promises more than the "claims" column. In particular, Timeout no longer says "produced no result" or "you can retry", as the Jira example did; see the plan for why.
3. Whether the repeated heading on the Error details page (the page title and the in-place "Error details" under its red notice) is acceptable.
4. Whether the failure notice at the top of the right-hand scrolling details panel is clear. It preserves preview/crop dimensions, and a new failure scrolls that panel to the notice. Guidance remains visible without expanding technical details; only its exact code starts collapsed. Evidence is off-screen at 96 DPI; live workstation acceptance is not claimed.

Record the decision (accepted, changes requested, or waived) on SCRUM-11151. Until then this acceptance item stays open.

When a trim editor closes after an integrity refusal, the unchanged Session_TrimAdjustClosed sentence is appended to the same failure notice. Its resource key is retained so the whole notice rewords on a language switch; the exact code and status/help line remain available. This is a display change, not a retry or reload.

Legacy diagnostic limit: the full attempt Description retains the original specialised Failure_* resource, which can still contain recovery advice or an older preservation claim. The new notice-only variants do not change persisted diagnostics. In particular, the two UnknownState notice variants explicitly allow partial work because the actual adapters can return them after an action or save was dispatched. This residual is disclosed; no global rewrite of specialised diagnostic descriptions is claimed.
