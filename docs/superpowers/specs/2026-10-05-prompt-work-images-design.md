## 1. 用户目标与已确认约束

操作者希望在 PrintFlow 内填写设计需求，自动得到常用生图 Prompt，尝试调用网页端 ChatGPT Work 生图，再让程序取得图片作为设计素材。自动生图失败时仍能获得可复制的完整 Prompt。

用户已确认：

- 使用已有个人 Plus／Pro 账号，不增加订阅。
- 优先使用免费方案；目前只有一台已有 Linux 服务器，可作为备用。
- 第一版采用已登录网页、本地接收和自动导入；Linux／MCP 中转留作可选扩展。
- 新功能与既有开发工作隔离。

此处的“免费”指不新增订阅、收费 API 或托管服务；生图仍受现有 ChatGPT 账号的额度和功能可用性限制。

## 2. 范围与验收结果

第一版交付一条单图片流程：

`设计需求 → 本地模板 Prompt → 网页生图尝试 → 接收一张图片 → 校验 → 准备设计素材`

包括：

1. 首页进入独立的“AI 设计素材”页面。
2. 本地参数化的常用模板，可预览、编辑和复制 Prompt。
3. 浏览器桥接具备可用条件时，一次按钮操作提交一个 Work 生图任务。
4. 按请求编号接收一张原始图片，自动导入现有素材准备流程。
5. 页面保留明确的阶段、停止操作和失败原因；任何自动化失败都保留 Prompt。
6. 用户手动完成生图后，可选择图片完成同一请求的素材导入。
7. 关联请求和导入会话，防止重复通知、重复点击和重启造成重复导入。

第一版不实现 Linux 服务部署、Google Drive／GCS 连接、MCP 上传服务、收费生图 API、参考图上传、批量生图、自动排版或直接生成生产 TIFF。它们不是本规格的验收条件。当前分支不合并、不发布，也不更改生产安装或签署的工作站基线。

## 3. 方案选择与能力边界

选择本地 Chromium 浏览器扩展与 .NET Native Messaging 宿主配合。扩展负责网页；宿主负责本机文件交接；PrintFlow 负责需求、请求记录、校验和导入。

默认试用浏览器为 Windows 上的 Microsoft Edge。Chrome 可以复用协议，但第一版自动化验收只要求一个经过实际验证的 Edge 配置。首次配置需要用户在该浏览器中登录 ChatGPT、加载本地扩展并登记其扩展 ID。缺少配置时 Prompt 功能照常可用，自动生图按钮说明缺少的条件。

这是一条需要真实网页验证的集成路线，不是已验证的成功承诺。浏览器扩展可以与本机宿主通信，不等于已经证明它可以完成 Work 生图。实现阶段必须验证 Work 入口、提交、生成结果和下载的完整链路。无法证明的操作不得标记为已支持。

未选择的路线：

- Linux／MCP 中转：适合以后增加云端文件交接，但需要可访问服务、认证和传图能力；第一版不为它增加部署依赖。
- 仅 Prompt：是内置降级路线，不满足自动生图的完整目标。
- Workspace Agent API：官方提供异步触发和状态查询，但需要工作区授权，不能据此推定当前个人账号拥有该能力；API 当前也不直接提供 Agent 的最终回复。
- 付费 Image API：不符合“不增加费用”的当前约束，不作为失败后的自动替代。

不调用 ChatGPT 未公开的后台接口，不复制登录 cookie，也不把 Codex 当前聊天中的工具当作 PrintFlow 可以直接调用的产品 API。

## 4. 操作者界面

“AI 设计素材”是导入前的独立入口，不新增生产工作流类型。页面依次展示设计需求、Prompt 和当前请求结果。

初始模板固定为三个可编辑的印花场景：

- **单主体素材**：主体、风格、颜色、背景要求、构图和期望比例。
- **徽章图案**：主体、形状、风格、色数、文字和期望比例。
- **文字印花**：必须保留的文字、字体风格、装饰元素、颜色和期望比例。

主体或文字等必要字段为空时说明具体缺失项，不生成无内容 Prompt。每个模板给出默认构图、清晰边缘、完整主体和避免水印等要求；用户可以修改最终文本。输入按原文保留，不依赖另一个语言模型进行翻译或改写。

生成用 Prompt 与交接指令分开存储。交接指令要求生成一张图片并提供可下载结果；请求编号属于任务元数据，不作为要画在图片上的内容。

操作包括“生成 Prompt”“复制 Prompt”“自动生图”“停止”“选择已生成的图片”和“返回首页”。有请求运行时禁用第二次提交；页面保留运行开始时的 Prompt 快照，编辑表单不改变已提交任务。“停止”在 Queued 至 Validating 阶段可用；Importing 阶段显示“正在导入”，暂时禁用停止，直到现有导入事务给出确定结果。

下载并导入成功后进入现有 Workflow Selection，预选“准备设计素材”，由操作者继续。导入不是设计审阅、背景透明确认或生产文件批准。实际尺寸和透明通道来自文件检测，不能由 Prompt 的要求推定。

Prompt、状态、错误和设置提示均提供现有中英文资源，与项目当前本地化方式一致。

## 5. 模块与接口职责

| 模块 | 职责 | 对外合同与依赖 |
| --- | --- | --- |
| Prompt 模板模块 | 校验输入、组合可编辑文本 | 输入模板 ID 和字段，返回文本或字段错误；纯逻辑，无网络和文件依赖 |
| 生图请求协调器 | 创建请求、保存阶段、处理停止与恢复 | 调用请求存储、生图通道、接收模块和导入入口；不识别网页控件 |
| Work 浏览器通道 | 操作专用 Work 页面、报告阶段、取得下载身份 | 接收请求编号、Prompt 快照和一次尝试编号；返回结构化状态或失败 |
| Native Messaging 宿主 | 扩展与本机请求文件、图片暂存的交接 | 仅接受登记的扩展来源；标准输入输出承载有长度前缀的 JSON，不混入日志 |
| 图片接收模块 | 校验下载身份、复制、检测并发布本地候选 | 返回应用拥有的候选引用、文件事实和哈希；不创建生产 Revision |
| 幂等导入入口 | 把候选交给现有素材导入流程 | 按请求编号最多关联一个 ProcessingSession；已有手动导入入口保持可用 |
| WPF 页面 | 展示需求、Prompt、进度和结果 | 仅依赖协调器视图合同，不直接操作浏览器、SQL 或任意文件路径 |

请求编号只是新功能请求的标识，不引入订单、客户或通用 Job 管理模型。自动生图通道与图片接收职责分开，后续 Linux／MCP 接收可以接在相同边界上，但本次不提供空壳服务器或假上传实现。

预期代码落点为现有 Domain／Workflow／Infrastructure／App 分层中的独立 AI 设计目录，另设浏览器扩展目录和小型 .NET 浏览器宿主项目。禁止把网页识别或接收逻辑塞进现有 Meitu／Photoshop 驱动。

## 6. 请求状态与持久化

状态采用有限、可测试的枚举：

`PromptReady → Queued → Submitted → Generating → Receiving → Validating → Importing → Imported`

其他结束状态：`PromptOnly`、`Cancelled`、`Interrupted`、`ImportFailed`。

- `PromptOnly`：通道未配置、未登录、功能或额度不可用、网页未识别、生成超时、结果不可下载或图片校验失败。保留 Prompt、最后成功阶段和原因。
- `Cancelled`：操作者停止；本次尝试禁止继续提交、接收或自动导入。操作者之后明确选择重试或手动图片时建立新的尝试编号。
- `Interrupted`：进程或桥接意外结束，无法证明请求的实际进度；重启后不自动重新生图。
- `ImportFailed`：已收到有效图片，但现有导入流程失败；保留本地候选和关联的会话身份，不重新生图。

每个请求持久化模板版本、字段、最终 Prompt 快照、状态版本、尝试编号、时间、拥有的标签页／对话身份、下载 ID、候选引用、哈希、导入会话 ID 和结构化失败。不得持久化账号密码或 cookie。

记录保存在当前配置的 Workspace Root 下的 `AiDesign/Requests/<requestId>/`。通过进程间独占更新与临时文件原子替换，保证 PrintFlow 和宿主不会各自覆盖对方状态。状态版本、尝试编号和随机交接令牌必须同时匹配才接受回报。

一台安装同时最多一个自动生图请求。准备 Prompt 不需要取得 Meitu／Photoshop 的工作站自动化锁；浏览器使用本功能自己的占用合同。

## 7. 网页操作与图片交接

1. PrintFlow 先保存 Prompt 和请求记录，再尝试取得浏览器通道。
2. 扩展为该请求创建专用 ChatGPT 标签页，确认已登录和 Work 模式。不能识别 Work 时返回失败，不静默改用普通 Chat。
3. 识别当前可见的输入与提交控件；记录提交身份后，最多提交一次。
4. 根据明确的生成中、错误和完成状态报告进度，不以固定等待时间或出现任意图片作为完成证据。
5. 完成时必须把新生成的单张图片绑定到本次对话和尝试；头像、旧图片、缩略图和其他标签页的图片不符合合同。
6. 使用经过验证的网页下载操作或网页已暴露的下载链接。通过浏览器下载 API 记录唯一 download ID 和完成后的文件位置；无法把下载唯一关联到该结果时返回 `PromptOnly`。
7. 宿主只接收该请求已登记的下载，检查配置的浏览器下载根目录、路径归属、普通文件属性和完整读取，再复制到本请求的暂存目录。不扫描整个下载目录寻找“最新图片”。
8. 接收模块检测真实内容，完成后原子发布候选。文件扩展名由真实 PNG／JPEG 类型决定。
9. PrintFlow 以应用拥有的候选引用和检测出的哈希调用素材导入入口；成功后展示对应会话。

Native Messaging 使用浏览器官方协议；登记限于当前 Windows 用户和本功能的宿主名、扩展 ID。第一版提供本地配套构建及显式登记／撤销步骤，不安装常驻服务、自动启动项或计划任务，也不发布扩展商店条目。

扩展只请求操作 ChatGPT 页面和完成上述交接所需的权限。第三方网页不能指定宿主执行命令或任意文件读写。

## 8. 文件检测与重复导入

第一版接受真实 PNG 和 JPEG；其他格式明确拒绝并提供手动回收提示。下载文件必须完整、非空且可以通过现有文件检测能力读取；上限为 40 MiB、64 百万像素。模板的目标比例、透明背景或印花适用性不是结构检测通过的依据。

候选先写到请求拥有的暂存文件，再按实际格式发布为最终候选；使用不会覆盖已有文件的命名和创建方式。接收期间损坏、中断或停止产生的暂存文件不进入导入入口。

导入关联必须在与新 ProcessingSession 的初始创建相同的 SQLite 事务内保存，并对请求编号设置唯一约束。不能在普通 `ImportAsync` 成功返回之后才写一份独立回执，否则崩溃窗口会重复创建会话。

新的幂等导入入口复用现有导入内部流程，按请求编号查找已有会话：

- 会话已导入成功：返回该会话，不复制第二次、不建立新 Revision。
- 会话已建立但导入失败或中断：返回同一会话及其实际状态，进入已有诊断／恢复路径。
- 尚未建立关联：原子建立关联和会话，再运行正常源文件快照、检测、哈希和 Revision 事务。

导入入口携带候选的预期哈希，并核对实际源快照的哈希；候选在交接后被改变时不能报告导入成功。浏览器只写接收候选，不能直接创建 Session、Revision 或批准记录。老的手动导入不要求请求编号。

## 9. 失败、停止与重启

所有失败保留可复制的 Prompt；失败提示区分网页提交、生图、下载、校验和导入。只有最终 `Imported` 可以称为已进入素材流程，网页提交成功不是生图成功。

生成尝试的总时限为 10 分钟，下载时限为 2 分钟。第一版不自动再次提交生图。用户明确重试会创建新的尝试编号，沿用或编辑 Prompt；旧尝试的迟到消息不能覆盖新尝试。

在允许停止的阶段接受“停止”时，使交接令牌失效并禁止本地自动导入；协调器串行处理停止与进入 Importing 的决定，确保二者不能同时被接受。它会尝试使用经过验证的网页停止控件，但只有得到网页确认才声明远端已停止；无法确认时说明远端任务可能仍继续。停止后的迟到下载不被自动采用。

重启把未完成的自动化请求显示为中断，保留 Prompt 和已收到的候选，不自动重新提交。操作者可选择继续接收已知候选或选择手动生成的图片；幂等导入入口保证不会建立第二个会话。

## 10. 设置与现有项目边界

AI 设计页面默认允许使用 Prompt。自动通道只有在浏览器扩展、宿主版本、扩展来源、下载根目录和网页适配检查通过时才可启用；否则页面展示具体原因。

默认接收目录随当前 Workspace Root 派生，不把真实图片、请求数据或账号信息写入代码仓库。单元和集成测试采用临时目录、合成图片与网页夹具，不使用客户作品和生产 Baseline。

既有 MVP 的本地处理、诊断和安装边界继续适用于旧流程。此次新需求只扩展独立的生成素材功能，不自动上传已有客户素材、生产证据或诊断包。

现有包策略禁止 Selenium／Playwright；本方案不引入这两个依赖。现有产品／安装边界测试广泛检查网络 API；第一版本地扩展与 stdio 交接不要求给 .NET 产品增加 HTTP 下载器。现有测试不能因为新功能失败而被删除或整体放宽。

## 11. 验证与交付判定

自动测试覆盖行为和重要故障窗口：

- 模板必填项、文字原样保留、Prompt 编辑后的提交快照。
- 通道未配置、未登录、额度不可用、未知网页和超时均保留 Prompt。
- 单次提交、重复通知、旧尝试回报、停止与迟到下载。
- 不属于本次请求的下载和路径、空文件、伪装扩展名、损坏或超限图片。
- 候选发布之前中断、导入事务之前／之后中断、重复导入与重启回收。
- WPF 运行中操作限制、Prompt-only 使用和中英文资源。
- 浏览器适配夹具中的 Work 模式、生成进度、结果识别和下载归属。

真实验证只针对用户已有账号和同意启用的试用浏览器配置：使用一条无客户内容的印花需求，完成自动提交、生成一张图片、本地回收、校验和导入；随后验证停止／通道断开时 Prompt 保留。

如果真实 Work 操作或下载链路不可实现，必须报告具体失败环节；不能仅凭模拟测试把自动生图标记为完成。可用的 Prompt 和手动回收能力单独报告为已完成部分。

本分支目前只准备书面规格。用户审阅本规格后，按 Superpowers 流程形成实施计划；计划审阅和执行方式选择完成后才写功能代码。

## 12. 来源与推断

- [ChatGPT Image generation](https://learn.chatgpt.com/docs/image-generation)：官方说明网页聊天的生图入口；网页能力和限额依赖账号与工作区设置。它不证明本扩展自动化已经可用。
- [Workspace Agent trigger runs](https://developers.openai.com/workspace-agents/trigger-runs)：异步触发、状态查询与当前无法直接检索 Agent 回复的限制。
- [Workspace Agent access tokens](https://developers.openai.com/workspace-agents/authentication)：工作区管理员设置和专用 token 的前提。
- [Microsoft Edge Native Messaging](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging)：扩展与本机 Win32 宿主的 stdio 通信、来源登记和当前用户注册方式。
- [Chromium Downloads API](https://developer.chrome.com/docs/extensions/reference/api/downloads)：下载身份、状态和本地文件信息的交接基础。
- 当前仓库：`ISessionService.ImportAsync`、`SessionService`、`IWorkspace`、`IFileInspector`、WPF 导航、本地化资源、中心包策略与安装边界测试。

“本地浏览器桥接可避免新增云托管费用”是本设计的工程选择；“可以可靠自动控制当前 Work 网页”仍需要实施阶段的真实证据。规格没有假设个人账号拥有 Workspace Agent API 权限，也没有假设 Linux 或 Google 服务已经配置完成。
